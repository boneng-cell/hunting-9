HUNTING PRINCIPLE

Think in this order:

UNTRUSTED INPUT ↓ PARSING / TRANSFORMATION ↓ VALIDATION ↓ TRUST DECISION ↓ PRIVILEGED OPERATION ↓ SECURITY BOUNDARY

Search for places where untrusted or lower-privileged data can influence a security-sensitive operation.

Always ask:

Where does the input originate?

Can an attacker control it?

How does it flow through the program?

Is it validated?

Is validation complete or bypassable?

Is it transformed before use?

Is quoting/escaping correct?

Does it reach a shell?

Does it reach a privileged operation?

Does it cross a user/root or untrusted/trusted boundary?

Can the behavior be reproduced safely?

What exact impact does it create?

FALSE POSITIVE FILTER

Before declaring a vulnerability, ask all of the following:

Is the attacker actually able to control the input?

Is there a realistic path to the vulnerable code?

Does it cross a meaningful security boundary?

Does Omarchy itself create the vulnerable condition?

Is it merely an upstream dependency vulnerability?

Does it require already-privileged access?

Is it only a hardening suggestion?

Is it only an informational weakness?

Is there actual reproducible impact?

Can the issue be reproduced against the latest relevant branch?

If the answer is no to the critical questions, do not report it as a confirmed vulnerability.
