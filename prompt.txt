CONTEXT

Repository:      https://github.com/Shopify/shipit-engine
Stars:           1.5k+
Primary Language: Ruby (Rails Engine)
Production Use:  Shopify's internal deployment coordination engine — "used to
                 synchronize and deploy hundreds of projects across dozens of
                 teams, using Python, Rails, RubyGems, Java, and Go"
Bug Bounty:      github.com/Shopify/* is IN SCOPE on HackerOne
Max Severity:    MEDIUM (source code reports are capped at Medium per H1 policy)
Critical Rule:   Finding must demonstrate REAL production deploy impact
                 (e.g., arbitrary shell on deploy runner, credential exfiltration,
                 deploy bypass, webhook forgery → unauthorized deploy)

Architecture Summary (from public docs + code inference):
  1. Shipit is a Ruby-on-Rails engine that acts as a deployment coordination tool.
  2. It receives GitHub webhooks (push, PR, status, check_suite, membership).
  3. It stores repository/stack configs in its database and syncs commits from GitHub.
  4. It reads shipit.yml FROM EACH DEPLOYED REPOSITORY to determine HOW to deploy.
  5. It spawns shell commands (via PTY.spawn) to execute deploy/rollback/dependency/
     fetch/task steps defined in shipit.yml.
  6. It runs merge-queue, CI status checks, lock/rollback/review-checklists.
  7. It integrates with GitHub (deploy statuses, merge requests).

Trust Model (CRITICAL for understanding attack surface):
  - shipit.yml is READ FROM DEPLOYED REPOSITORIES — user-controlled content.
  - Deploy steps are executed as shell commands on SHIPIT's deploy runners.
  - The deploy runner has GITHUB_TOKEN, SSH keys, and access to prod infrastructure.
  - Authentication can be WHOLLY DISABLED via env var (SHIPIT_DISABLE_AUTH).
  - Webhook signature verification can be disabled (missing webhook_secret).

Attack Surface Summary (preliminary ranking — to be validated):
  [CRITICAL] Shell command injection via shipit.yml deploy steps
  [CRITICAL] Auth bypass via SHIPIT_DISABLE_AUTH / disable_api_authentication
  [CRITICAL] Webhook signature bypass (missing webhook_secret)
  [HIGH]     Env var injection via machine.environment (bypasses whitelist)
  [HIGH]     ${VAR} shell expansion bypass (interpolate regex gap)
  [MEDIUM]   Path traversal via shipit.yml inherit_from / machine.directory
  [MEDIUM]   Repository owner/.. path traversal (regex allows dots)
  [MEDIUM]   X-Shipit-User header impersonation
  [LOW]      SafeYAML deserialization (safe mode mitigates but Paquito allows HWI)
  [LOW]      Format string in TaskDefinition#render_title

PHASE 2 — VULNERABILITY HYPOTHESIS VALIDATION (PARALLEL SUBAGENTS)
───────────────────────────────────────────────────────────────────
Goal: Validate or refute each preliminary vulnerability hypothesis with
      concrete code evidence.

Each hypothesis must be assigned to a dedicated subagent. Subagents MUST:
  a) Read the relevant source files from Phase 1 (not from memory).
  b) Trace the data flow from user-controlled input to the security-sensitive
     sink.
  c) Identify any existing sanitization, validation, or mitigation.
  d) Determine if the vulnerability is actually exploitable in a realistic
     Shopify production scenario.
  e) Output: A verdict (VALID / INCONCLUSIVE / INVALID) with supporting
     code quotes and reasoning.

Subagent Tasks:

  SUBAGENT A — Shell Injection via shipit.yml (H1)
  ──────────────────────────────────────────────────
  Question: Can an attacker with write access to a deployed repository's
            shipit.yml achieve arbitrary shell execution on the deploy runner?

  Trace:
    shipit.yml (from repo)
      → SafeYAML.load (file_system.rb)
      → config['deploy']['override'] / config['rollback']['override'] /
        config['tasks'][name]['steps']
      → DeploySpec#deploy_steps! / TaskDefinition#steps
      → TaskCommands#perform → Command.new(command_line as STRING)
      → Command#start → PTY.spawn(unbundled_env, *interpolated_arguments)

  Key questions to answer:
    - Are deploy steps passed as a single string or an array of arguments?
      (Single string → /bin/sh -c → full shell interpretation)
    - Is there any sanitization of the command string before PTY.spawn?
    - Does the Trust Boundary (PR vs. target branch) prevent untrusted
      shipit.yml from being executed?

  SUBAGENT B — Auth Bypass via SHIPIT_DISABLE_AUTH (H2)
  ──────────────────────────────────────────────────────
  Question: Can an attacker bypass all web authentication by setting
            SHIPIT_DISABLE_AUTH?

  Trace:
    ENV['SHIPIT_DISABLE_AUTH'] (lib/shipit.rb:55)
      → authentication_disabled? (lib/shipit.rb:88)
      → AnonymousUser#authorized? (app/models/shipit/anonymous_user.rb)
      → force_github_authentication (authentication.rb:11-25)

  Key questions:
    - Is SHIPIT_DISABLE_AUTH ever set in production?
    - What is the default behavior if the env var is absent?
    - Does disable_api_authentication have the same effect on the API?

  SUBAGENT C — Webhook Signature Bypass (H3)
  ───────────────────────────────────────────
  Question: Can an attacker forge arbitrary GitHub webhooks if webhook_secret
            is not configured?

  Trace:
    webhook_secret (github_app.rb:54)
      → verify_webhook_signature → return true unless webhook_secret
      → webhooks_controller.rb:15 → verify_signature

  Key questions:
    - Is webhook_secret required by the default configuration?
    - What happens in the Shopify production deployment?
    - Does GitHub now use SHA256 while the code only checks SHA1?

  SUBAGENT D — ${VAR} Shell Expansion Bypass (H5)
  ────────────────────────────────────────────────
  Question: Does environment_variables.rb's interpolation regex fail to catch
            ${VAR} syntax, allowing shell expansion?

  Trace:
    environment_variables.rb:23 — argument.gsub(/(\$\w+)/)
      → Matches $WORD only, NOT ${VAR}, $(), or backticks
      → Unmatched syntax passes through to PTY.spawn
      → /bin/sh expands ${VAR} as an environment variable

  Key questions:
    - Can this be combined with machine.environment to set arbitrary vars?
    - Are backticks or $() also able to bypass interpolation?
    - What is the impact of shell expansion in this context?

  SUBAGENT E — Path Traversal via inherit_from / machine.directory (H6, H7)
  ──────────────────────────────────────────────────────────────────────────
  Question: Can shipit.yml use inherit_from or machine.directory to traverse
            outside the repository directory?

  Trace:
    inherit_from: path.dirname.join(config_obj.delete('inherit_from'))
      → No sanitization of ../ sequences (file_system.rb:91)
    machine.directory: File.join(@app_dir, directory) (file_system.rb:31)

  Key questions:
    - Are there any checks preventing directory traversal?
    - What files could be read via inherit_from?
    - What is the impact of escaping the working directory?

  SUBAGENT F — X-Shipit-User Impersonation (H9)
  ──────────────────────────────────────────────
  Question: Can an authenticated API client impersonate any user via the
            X-Shipit-User header?

  Trace:
    X-Shipit-User header (api/base_controller.rb:57-61)
      → User.where('lower(login) = ?', user_login.downcase).first
      → No validation that the user is associated with the API token

  Key questions:
    - Is the X-Shipit-User header validated against the API token?
    - What privileges does the impersonated user gain?
    - Is this an intended feature or a security gap?

Method:

CONSTRAINTS & RULES (NON-NEGOTIABLE)

  1. NO GIT CLONE — Use GitHub's REST API and raw content URLs exclusively.
  2. NO THEORETICAL FINDINGS — Every claim must be backed by code evidence and
     a plausible exploitation path in Shopify's production environment.
  3. ONE CONFIRMED FINDING IS ENOUGH — Do not pad the report with low-quality
     observations. Quality over quantity.
  4. PoC MUST BE FUNCTIONAL — Not just a curl command that returns 404. Show
     real impact (e.g., shell output, file read, credential exfiltration).
  5. ASK CLARIFYING QUESTIONS — If a condition is unclear (e.g., "Is webhook_secret
     set in production?"), ask before making assumptions.
  6. STOP AFTER CONFIRMATION — Once a vulnerability type is confirmed, do not
     continue testing that type. Focus on breadth across different types.
